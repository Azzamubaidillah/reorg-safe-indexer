# Runbook

How to deploy, check and repair a running instance. Settings and CLI commands are listed in [operations.md](operations.md); what each failure means and which test proves the behaviour is in [failure-modes.md](failure-modes.md). Commands below use `<indexer-image>`, `<api-image>`, `<env-file>` and `<db>` as placeholders.

Where a step is a manual procedure that no test covers, it says so.

## Deploy

### Images

Three images, all built from the repository root:

| Image | Build | Notes |
|---|---|---|
| Indexer | `docker build -t <indexer-image> .` | Runs `node --import tsx apps/indexer/src/main.ts run`; non-root user; no build step |
| API | `docker build -f apps/api/Dockerfile -t <api-image> .` | Listens on `API_PORT` (3200) and binds `API_HOST=0.0.0.0` inside the image. `/data/analytics` is the Parquet volume and must be writable, since `verify` writes a scratch copy beside it |
| Dashboard | `docker build -f apps/web/Dockerfile --build-arg API_URL=http://<api-host>:3200 -t <web-image> .` | `API_URL` is baked in at build time (it becomes a rewrite target), so a different API address needs a rebuild. Serves on 3100 |

### Env files

Keep them out of git; the indexer's and API's contain a database password and possibly a Telegram token.

Indexer (all variables in [operations.md](operations.md)):

```
DATABASE_URL=postgres://<user>:<password>@<db-host>:5432/<db>
CHAIN_ID=1
RPC_PROVIDERS=[{"name":"a","url":"https://...","maxSpan":100,"rps":15,"batchSize":20},{"name":"b","url":"https://...","maxSpan":10,"rps":15,"batchSize":20}]
START_BLOCK=<first block, required on an empty database>
RECONCILE_PROVIDER={"name":"c","url":"https://...","maxSpan":100,"rps":5}
METRICS_PORT=3300
METRICS_HOST=<loopback or a private interface>
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
```

- Provider order is preference order. Put the provider you trust most first (see [mismatch playbook](#reconciliation-mismatch)).
- `RECONCILE_PROVIDER` must have a name that is not in `RPC_PROVIDERS`, and should be a different operator from the ingest providers. Unset, reconciliation is off.
- With the Telegram variables blank, alerts are only log lines with an `alert` field at warn level. Decide deliberately whether that is acceptable; nothing pages you.
- `START_BLOCK` must stay the same for the life of the database: a run refuses to resume if the first committed range starts elsewhere.

API: `DATABASE_URL`, `CHAIN_ID`, `ANALYTICS_DIR=/data/analytics`, optionally `ANALYTICS_EXPORT_INTERVAL_MS` (unset means the API never exports), `API_CORS_ORIGIN`.

The API only reads. Give it a database user that has `SELECT` on the `chain` and `ops` schemas and nothing else, with a short `statement_timeout` (10 s) so a slow public request cannot hold a connection. The repository does not create that role, so this is a deployment step.

Do not run the Parquet export inside the API under that role. The export rewrites a whole UTC day from Postgres, and once a day holds a few hundred thousand rows its queries exceed a 10 s timeout, so exports fail and the store stops advancing (seen in the live deployment after one full day). Run the analytics CLI `export` on a schedule in its own container instead (for example `while true; do node --import tsx packages/analytics/src/cli.ts export --dir /data/analytics; sleep 600; done` in the API image), as a separate read-only user with a longer timeout (10 min), and leave `ANALYTICS_EXPORT_INTERVAL_MS` unset on the API. Run the analytics `verify` right after an export: it compares against live Postgres, so ranges published since the last export show up as missing coverage on the open day.

### Migrations

The migration runs from any image that contains `packages/db` (indexer and API do):

```sh
docker run --rm --env-file <env-file> <indexer-image> packages/db/src/migrate.ts
```

Run it before starting a new version. Migrations are generated by Drizzle and are additive so far (`0000` base tables, `0001_ops_reorgs`, `0002_ops_quality_reconciliation`, `0003_ops_range_retention`, `0004_ops_reorg_ack`). `0004` marks halts recorded before it as acknowledged so the upgrade cannot block a running indexer. Take a backup first; there are no down migrations.

### Start order and supervision

1. Database up, migrations applied.
2. Indexer: `docker run -d --env-file <env-file> <indexer-image>`.
3. API with the analytics volume mounted, then the dashboard.

Exit codes of `run`: 0 finished or interrupted, 1 error or lock held, **2 reorg at or below the finalized block**. Restarts are harmless after a halt: the halt is recorded in `ops.reorgs` and stays in force until acknowledged (ADR-023). While an unacknowledged halt exists, `run` takes the lock, logs `halted: unacknowledged reorg #<id>`, sends a `halt-unacknowledged` alert, records a failed run and exits 2 again, all before any RPC call. So Docker's `restart: on-failure`, which cannot exclude one exit code, costs one database round trip per restart and nothing else. Expect a stream of failed runs in `ops.runs` and repeated alerts (de-duplicated by `ALERT_COOLDOWN_MS`) until you run `ack-halt`; a supervisor that backs off, or `RestartPreventExitStatus=2` under systemd, only makes that quieter.

Stop with SIGTERM: the timers stop, running cycles finish and the run ends as `failed/interrupted`. `kill -9` is also safe for the data (ADR-005) but leaves the run row `running` until the next start marks it `failed/abandoned`.

## Routine checks

Daily, or when an alert fires:

| Check | Command | Healthy |
|---|---|---|
| Liveness | `curl <metrics-host>:3300/healthz` | 200. 503 means no head poll or commit for `HEALTH_STALE_AFTER_MS` (60 s default) |
| Positions and counts | `curl <metrics-host>:3300/status` (or the API's `/v1/status`, which needs only the database) | head lag small (a few blocks), ranges at or below `finalized` all `published`, `failed` is 0, `backfillJobs.open` is 0, `reconciliation.unexplained` is 0 |
| Lag over time | `main.ts lag-report --since 24h` | `headLag.p95` and `finalizedLag.p95` low; `samples` covers the window |
| Unexplained mismatches | `main.ts reconciliations --unexplained` | `[]` |
| Integrity | `main.ts verify` | exit 0, `"problems": []` |
| Decoded tables vs landing | `main.ts rebuild-verify` (reads everything; run off-peak) | exit 0, `equal: true` |
| Parquet vs Postgres | `node --import tsx packages/analytics/src/cli.ts verify` in the API image, ideally when the indexer is idle | all checks pass |

Run the CLI commands in a one-off container: `docker run --rm --env-file <env-file> <indexer-image> apps/indexer/src/main.ts <command>`. `verify`, `reconciliations`, `explain-reconciliation` and `lag-report` need only `DATABASE_URL` and `CHAIN_ID`; `rebuild-verify` needs the full `run` environment.

Prometheus series (from `/metrics`): `indexer_head_block`, `indexer_finalized_block`, `indexer_stored_tip_block`, `indexer_head_lag_blocks`, `indexer_finalized_lag_blocks`, `indexer_reorgs_total{action}`, `indexer_reorg_depth`, `indexer_ranges_committed_total`, `indexer_logs_committed_total`, `indexer_quality_gate_failures_total`, `indexer_reconciliation_mismatches_total`, `indexer_rpc_calls_total`, `indexer_rpc_retries_total`.

## Reading the gates

Seven gates run per range, in this order, once the range ends at or below the finalized block. Results are in `ops.quality_results` (one row per range and gate, latest only):

```sql
select from_block, gate, rows_checked, rows_failed, detail
from ops.quality_results
where chain_id = 1 and not passed
order by from_block, gate;
```

| Gate | A failure means | `detail` looks like |
|---|---|---|
| `decode_rejects_zero` | Logs that matched the filter did not decode (wrong topic count, malformed data) | `rejected_logs=N` |
| `counts_consistent` | Row counts in the tables disagree with the range row, or `logs != transfers + swaps + rejects` | `logs(recorded 83, stored 82)=1` |
| `blocks_linked` | A missing block, a broken parent link, or the first block not extending the stored block below | `broken_links=1`, `missing_blocks=1`, `broken_boundary=1` |
| `log_positions_unique` | The same log position twice, in `logs` or across decoded tables | `duplicate_logs=N` |
| `log_block_hash_matches` | A log's block hash differs from the stored header at its height, or has no header | `wrong_hash=N`, `no_block=N` |
| `value_bounds` | A hash, address or amount outside its type (uint256, int256, uint160, uint128, tick range) | `bad_transfers=N` |
| `decoded_matches_landing` | A decoded row with no matching landing log, or a tracked landing log with no decoded row (beyond counted rejects) | `transfers_without_log=N`, `undecoded_logs=N` |

A failed range has `ops.ranges.status = 'failed'` and one job in `ops.backfill_jobs` whose `failure_reason` lists the failing gates. The dashboard's quality page shows the same thing. The M3 gate wants every finalized range `published`, no `failed`, no open jobs and no unexplained mismatch ([operations.md](operations.md#reading-the-m3-gate-inputs)).

## Incident playbooks

### Halt below finalized

Symptom: `run` exited with code 2, a `fatal` log line `reorg` with `action: halted`, a halt alert, `ops.runs.failure_reason` starting with `reorg below finalized`, and an `ops.reorgs` row with `action = 'halted'`. Nothing was deleted.

1. **Do not acknowledge yet.** A finalized-block reorg should be impossible on Ethereum; the likelier explanations are a bad provider or bad stored data. Restarts before the acknowledgement just exit 2 again.
2. Read the audit row:
   ```sql
   select detected_at, fork_block, depth, finalized_block, orphaned, canonical
   from ops.reorgs where action = 'halted' order by id desc limit 1;
   -- add `id, acknowledged_at` to see whether it is still blocking

   ```
   `orphaned` is what is stored; `canonical` is what the provider reported at those heights. The true fork is at or below `fork_block`, because the search never looked lower than the finalized block.
3. Ask at least two other independent providers for the block hash at several heights from `fork_block` upward and compare with both lists. Decide which is wrong:
   - **The stored data is wrong** (the indexer ingested a bad chain view earlier, or a provider served bad data): continue to step 4.
   - **The provider that disagreed is wrong** (stale or misbehaving): the stored data is fine. Fix `RPC_PROVIDERS` (remove or demote it), then continue at step 6.
   - **All independent providers agree with the new chain and the finalized block really moved**: that would be a chain-level event. Do not repair; stop and investigate before touching data.
4. Repair by hand (no tool exists for this and no test covers it; it follows `rollbackTo` in `apps/indexer/src/store.ts`). Find the highest stored height `A` whose hash matches the independent providers. In one transaction, with the indexer stopped: delete every row in `ops.ranges` whose `to_block > A`, take `F` as the lowest `from_block` among them, and delete `chain.erc20_transfers`, `chain.uniswap_v3_swaps`, `chain.logs` (by `block_number >= F`) and `chain.blocks` (by `number >= F`) for the chain. Whole ranges go, as in an automatic rollback. Quality rows and jobs for deleted ranges can stay; they are keyed by range and resolve as obsolete.
5. Run `verify`. If published ranges were removed, the Parquet store contains data that no longer exists in Postgres. The files are derived (ADR-015), so re-exporting repairs them, but only if no decoded rows were purged: once `DECODED_RETENTION_DAYS` has purged a day, the Parquet files are the only copy of it and must not be deleted (the exporter refuses to rewrite such a day anyway). Check `/v1/status` `retention.decodedPurgedThroughBlock` against the blocks you removed; if the ranges you removed overlap purged days, stop: the Parquet files for those days are the only copy and the removed Postgres rows were already gone. Then run the analytics `verify`.
6. **Acknowledge, then restart.** `ack-halt` needs only `DATABASE_URL` and `CHAIN_ID`:
   ```sh
   main.ts ack-halt <reorgId> "<what was found and what was done>"
   ```
   The text must not be empty and is stored with the row. Only an unacknowledged `halted` row takes it. Then restart `run`. If the provider still serves the fork below the finalized block, the run halts again as a new row and blocks again, which is the correct outcome; go back to step 2 for the new row.

### Reconciliation mismatch

Symptom: a `Reconciliation mismatch` alert, `reconciliations --unexplained` listing rows.

1. Read each row: `hash_mismatches` (height, stored hash, observed hash or `null`), `stored_log_count`, `observed_log_count`.
   ```sql
   select id, from_block, to_block, provider, hash_mismatches, stored_log_count, observed_log_count
   from ops.reconciliations where status = 'mismatch' and (explanation is null or explanation = '') order by id;
   ```
2. Ask a third provider for the same block hashes and for `eth_getLogs` over the range (same addresses, topic0 `Transfer` and `Swap`). Decide which side is wrong.
3. **The second source was wrong or behind** (common: a lagging node, or a provider with a range cap that truncated): record why.
   ```sh
   main.ts explain-reconciliation <id> "second source returned 82 of 83 logs; third provider and stored agree"
   ```
4. **The stored data is wrong**: repair the range through the backfill machinery. Put the correct provider first in `RPC_PROVIDERS` (backfill uses the first provider that is not cooling down), restart, then force the range through a job (manual; the backfill path itself is tested, this entry point is not):
   ```sql
   update ops.ranges set status = 'failed', published_at = null where chain_id = 1 and from_block = <from>;
   insert into ops.backfill_jobs (id, chain_id, from_block, to_block, status, failure_reason)
   values ('1:<from>-<to>', 1, <from>, <to>, 'queued', 'manual: reconciliation mismatch <id>')
   on conflict (id) do update set status = 'queued', failure_reason = excluded.failure_reason, resolved_at = null;
   ```
   The next quality cycle re-fetches the range, replaces it only if the new headers link to the stored neighbours, re-runs the gates and publishes it. Then explain the mismatch row with what you found. The Parquet day containing the range is rewritten from Postgres at the next export; check with the analytics `verify`.
5. A mismatch where the observed side is `null` at a height only means the second source has no logs there; compare log counts first.

### Stuck backfill

Symptom: `backfillJobs.open` stays above 0 for more than a few cycles; a failed gate alert that repeats.

```sql
select id, status, attempts, failure_reason, updated_at
from ops.backfill_jobs where status <> 'resolved' order by updated_at;
```

Read `failure_reason`; it is the last reason for requeue:

| Reason | Meaning | Action |
|---|---|---|
| `backfill failed: ...` (RPC error, timeout) | Provider trouble | Check providers; the job retries by itself every cycle |
| `backfill refused: re-fetched block ... does not link to stored block ...` | The re-fetched chain differs from a neighbouring stored range. Either the provider is wrong, or the neighbour is. Never auto-fixed so that a repair cannot break the chain | Compare hashes at the boundary with two providers. If the neighbour is wrong, treat it as the stored-data-wrong case above for that range |
| `still failing after backfill: <gate>` | The fresh data fails the same gate. Often a data-shape issue the decoder does not accept (for example a new log shape) rather than corruption | Read `ops.quality_results.detail`; look at the offending rows; fix the decoder or the expectation in code, then let the next cycle re-gate |
| `obsolete (...)` | Range changed under the job; resolved by itself | None |

`attempts` increments on every try, but there is no retry cap: a job that cannot be repaired is retried indefinitely, two per cycle (`QUALITY_MAX_BACKFILLS`), least-recently-touched first.

### Provider outage

Symptom: `indexer_rpc_retries_total` rising, `rpc retry` warn lines, head lag growing, `/healthz` 503 if everything is down, or `run` exited 1 with `run-crash`.

1. One provider failing: the pool already rotates; no action unless it is the one carrying most traffic and it is slow. Check `ops.runs.rpc_calls` for per-provider call counts.
2. Provider timing out or rate-limiting steadily: lower its `rps` or `batchSize`, or move it down the list, and restart.
3. All providers failing: wait or add a provider to `RPC_PROVIDERS` and restart. Committed ranges are safe; the indexer resumes at the next uncommitted range. No data repair is needed after an outage.
4. After recovery, `lag-report --since 1h` should return to normal and `verify` should be ok.
5. Providers that start returning pruned or unsupported errors for old ranges show up as `unsupported` failovers; if a backfill needs old blocks, put an archive-capable provider first.

### Indexer crashed or was killed

Restart it. It marks the old run `failed/abandoned`, takes the lock, and resumes at one past the last committed range; no manual step. If it exits 1 immediately with "another indexer holds the lock", another process (or a connection that has not yet timed out) holds the advisory lock for that chain; find and stop it.

### Disk filling up

Retention is the control, but nothing in the code watches disk. Watch the database volume yourself. With `LANDING_RETENTION_DAYS=7` and `DECODED_RETENTION_DAYS=14` the size settles at a few GiB plus a few MiB a day for blocks ([costs-and-load.md](costs-and-load.md#storage)). Growth well above that means retention is not running or is blocked:

1. `main.ts retention --dry-run` shows what a cycle would purge and `manifestProblem` (missing or foreign manifest, so decoded rows are kept).
2. `/v1/status` `retention` shows how far each purge has reached.
3. Landing logs are kept for ranges with no `match` row while the reconciler is active; look for failed or unreconciled ranges (`reconciliations --unexplained`, failed ranges, reconciler alerts).
4. Deleted rows free space for reuse inside Postgres; they do not shrink the files. Size settles at the peak of the retained window, so an increase of retention days only grows the database. To give space back to the operating system you need `VACUUM FULL` or a dump and restore, which lock tables; this is a manual maintenance step and is not tested here.

If the volume fills anyway, Postgres stops writing, the run fails, and it resumes after space is freed. Do not delete from `chain.*` by hand; use the retention settings.

### Database lost

1. Restore the most recent backup (backups are your responsibility; none are made by this repo), run migrations, start the indexer with the same `START_BLOCK`. It resumes after the last restored range.
2. With no backup, start from `START_BLOCK` on an empty database; ingestion is deterministic, and the M1 gate backfilled 50,000 blocks in about an hour on keyless endpoints ([m1-gate.md](m1-gate.md)). Ops history (reorgs, reconciliation explanations, lag samples) is lost and cannot be refetched.
3. Re-export the Parquet store only if no decoded rows were purged. If `DECODED_RETENTION_DAYS` has been in use, the Parquet files may hold the only copy of old days: keep them, and expect the restored database to lack the decoded rows for those days (`/v1/transfers` and `/v1/swaps` stay empty for them; analytics endpoints still serve them). The exporter will refuse to rewrite a purged day, which is the intended protection.
4. Run `verify`, `rebuild-verify` and the analytics `verify`.

## Retention

Retention deletes data that can be obtained again and never touches what cannot. Design and reasons: [decisions.md](decisions.md#adr-020-retention-by-reacquirability). Full variable list and what each consumer does with purged ranges: [operations.md](operations.md#retention).

| Class | Tables | Policy |
|---|---|---|
| Landing logs | `chain.logs` | Purged per range after `LANDING_RETENTION_DAYS` (default 7) |
| Decoded rows | `chain.erc20_transfers`, `chain.uniswap_v3_swaps` | Purged per range after `DECODED_RETENTION_DAYS` (unset: kept forever) |
| Irreplaceable | `chain.blocks`, every `ops.*` table | Never deleted |

### Turn it on

On the indexer:

```
LANDING_RETENTION_DAYS=7
DECODED_RETENTION_DAYS=14
ANALYTICS_MANIFEST_PATH=<analytics dir>/_manifest.json
RETENTION_INTERVAL_MS=3600000
RETENTION_MAX_RANGES=500
```

- The indexer needs read access to the manifest file (mount the analytics volume read-only into the indexer container). The process refuses to start with `DECODED_RETENTION_DAYS` set and no `ANALYTICS_MANIFEST_PATH`.
- The API process must have the same `LANDING_RETENTION_DAYS` and `DECODED_RETENTION_DAYS`, otherwise `/v1/status` reports them as null.
- The Parquet export must be running (the analytics CLI `export` on a schedule, as described under [Env files](#env-files)). Decoded rows are only purged for blocks the manifest lists as exported.
- Start with landing only, watch a few cycles, then add the decoded setting.

### Before and after

1. `main.ts retention --dry-run` prints JSON with `landing` and `decoded` (the ranges the next cycle would purge) and `manifestProblem`. It writes nothing; without the flag the command only prints usage, and purging happens in the `run` timer. The M3 test "retention --dry-run lists what would be purged without writing, and refuses to run without the flag" covers it.
2. Check that landing purges are not skipping ranges for a reason you care about. With the reconciler active a range is purged only with a `match` row, so ranges with a mismatch or no row keep their logs on purpose. If many ranges are not purging, look at reconciliation first.
3. For decoded purges: run the analytics `verify` and confirm the manifest covers the days you are about to purge. A UTC day that contains an unexported range is held back as a whole.
4. After a cycle: `main.ts verify` (exit 0; its `purged` field counts the ranges whose parts were skipped) and `main.ts rebuild-verify` (exit 0; `skippedRanges` counts ranges left out because their logs are gone).

### The Parquet store becomes the only copy

Once decoded rows of a day are purged, the Parquet files for that day are the only copy of those rows in the system. Consequences you need to act on:

- **Back up the analytics volume** like the database. It is no longer rebuildable from Postgres for purged days.
- **Never delete or recreate the analytics directory or its manifest** once decoded purges have happened. Without the manifest the exporter would rebuild days from Postgres, find them purged, and refuse: it throws `refusing to export: day(s) ... contain ranges whose decoded rows were purged` before writing anything. That protects the files, and it also means recovering from a deleted store is not possible for those days by this system (landing logs may be refetched by hand and re-decoded; there is no tool or test for it).
- `/v1/transfers` and `/v1/swaps` return no rows for decoded-purged ranges. `/v1/analytics/*` still serves those days.
- Lowering `DECODED_RETENTION_DAYS` later purges more; raising it does not bring anything back.

### What coverage you lose

`rebuild-verify` and the `decoded_matches_landing` gate read landing logs, so for a purged range they no longer prove anything. The gates only run on candidates, so purged (published) ranges are not re-gated; `verify` keeps checking blocks, links and range counts for every range. Reconciliation skips landing-purged ranges, which is why landing is purged only after a `match` row exists.
