# Failure modes

What can go wrong, how the system notices, what it does, and which test shows it. Test paths are relative to the repository root; `*.int.test.ts` files need Postgres, the Anvil file needs `anvil`. Design reasons are in [decisions.md](decisions.md), response procedures in [runbook.md](runbook.md).

"No test" is stated where it is true. A row without a test is a gap, not a guarantee.

## Provider and network

| Failure | Detection | Behaviour | Proof |
|---|---|---|---|
| Provider rejects an `eth_getLogs` span (limit or too many results) | Message/status classified as `range_too_large` (patterns taken from real provider answers) | The span is halved and retried on the same provider, down to one block, then the error propagates. Logs are neither lost nor duplicated and come back sorted. `maxSpan` per provider pre-chunks requests | `apps/indexer/test/fetcher.test.ts` ("halves on range_too_large without losing or duplicating logs", "halves down to a single block, then gives up"); `apps/indexer/test/rpc/errors.test.ts` (real messages, and generic `-32000` never becomes a span error); `apps/indexer/test/rpc/pool.test.ts` ("range_too_large propagates immediately without retry or failover") |
| HTTP 429 or rate-limit message | Status 429 or message pattern; `Retry-After` parsed (seconds or HTTP date) | The provider cools down for `Retry-After` or the backoff and the next provider takes the call; if all are cooling, the pool waits for the soonest. A client-side token bucket per provider (`rps`) avoids most 429s | `apps/indexer/test/rpc/pool.test.ts` ("rate_limited on A moves to B; A is not reused before its Retry-After elapses", "waits for the soonest provider when all are cooling down"); `apps/indexer/test/rpc/provider.test.ts` (429 with Retry-After); `apps/indexer/test/rpc/limiter.test.ts`. Seen live: 1 rate-limit response in the M1 run ([m1-gate.md](m1-gate.md)) |
| Provider timeout, 5xx, non-JSON body, network error | Classified `transient` | Exponential backoff (500 ms doubling, capped at 30 s), rotate providers, give up after 8 attempts and fail the run. Seen live: 12 timeouts (30 s request timeout) in the M1 run, each retried on the next provider with no data effect | `apps/indexer/test/rpc/provider.test.ts` (502, non-JSON, network failure, missing id); `apps/indexer/test/rpc/pool.test.ts` ("throws the last RpcError once maxAttempts is exhausted, backing off exponentially") |
| Provider refuses the request (pruned history, disabled method, 401/403, plan limit) | Classified `unsupported` | Skipped for the rest of that operation and the next provider is tried without splitting. Throws if every provider refuses | `apps/indexer/test/rpc/pool.test.ts` ("unsupported on A fails over to B...", "throws when every provider is unsupported"); `apps/indexer/test/rpc/errors.test.ts` |
| All providers down | Every attempt fails; the pool throws after its attempt budget | The `run` ends as `failed`, exit code 1, `run-crash` alert. Committed ranges are untouched, a restart resumes. `/healthz` goes 503 after `HEALTH_STALE_AFTER_MS` if the process stays up but cannot poll | `apps/indexer/test/rpc/pool.test.ts` (attempt budget); `apps/indexer/test/status.int.test.ts` (healthz flips to 503 and recovers). No test of a full multi-minute outage |
| Provider answers inconsistently: logs from one chain view and headers from another, a node behind its peers, a removed log, a missing header | `validate` in the fetcher: header numbers and parent links, every log's `blockHash` equals its header, no `removed`, no log outside the range | The range is not stored. It is refetched up to 8 times with backoff (cap 4 s); if it still fails, the run fails. Headers and logs are always taken from one provider so they describe one view | `apps/indexer/test/fetcher.test.ts` ("rejects a broken parent-hash link", "rejects a log whose blockHash differs from the header", "rejects removed logs", "re-fetches a range whose logs disagree with its headers until the node catches up", "gives up after the retry bound"); `apps/indexer/test/reorg.int.test.ts` ("re-fetches ranges whose logs come from the old chain while headers are already new, then converges") |
| Provider silently omits logs but is self-consistent | Not visible to the gates. The second-source reconciler compares log identities and counts against a different provider | A `mismatch` row is written, an alert fires, and the mismatch stays "unexplained" until a human records an explanation | `apps/indexer/test/reconcile.int.test.ts` ("flags a log the second source is missing, with both counts"); `apps/indexer/test/m3-e2e.int.test.ts`. If both providers share an upstream node and agree, this is not detected |
| Second source unavailable or behind | Fetch error or header missing for the range | No row is written (not a mismatch), the failure is counted in the cycle summary, and the range is retried next cycle | `apps/indexer/test/reconcile.int.test.ts` ("writes no row when the provider fails...", "treats a second source that has not reached the range yet as an error, not a mismatch") |

## Process and database

| Failure | Detection | Behaviour | Proof |
|---|---|---|---|
| Crash or `kill -9` mid-batch | On restart the `ops.runs` row is still `running` while the advisory lock is free | The stale run is marked `failed/abandoned`. Resume starts at one past the last committed range; in-flight ranges are refetched. A range is committed in one transaction, so there is no partial range | `apps/indexer/test/crash-resume.int.test.ts` ("resumes after SIGKILL mid-run with no gaps, no duplicates, and exactly the expected rows"); `apps/indexer/test/store.int.test.ts` ("is atomic: a failure after the data inserts leaves no partial range behind"); live: [m1-gate.md](m1-gate.md) (6,000 blocks committed before the kill, 0 gaps, 0 duplicates) |
| Two indexers started for one chain | `pg_try_advisory_lock` fails | The second exits 1 with an error and touches nothing; the first continues | `apps/indexer/test/crash-resume.int.test.ts` ("refuses a second concurrent run...") |
| A range is re-committed with a different payload (provider returned different data for the same blocks) | `payload_sha256` differs from the stored one | `PayloadMismatchError`; nothing written. An identical payload is a no-op | `apps/indexer/test/store.int.test.ts` ("recommitting an identical range reports already_committed", "rejects a different payload for an already committed first range", "rejects a mid-chain range whose logs differ by one row, even though headers still link") |
| Resume with a different `START_BLOCK` than the stored history | `resumePoint` compares first stored range with `START_BLOCK` | Refuses to start | `apps/indexer/test/store.int.test.ts` ("refuses to resume when the committed ranges start somewhere else") |
| Memory growth over a long run (the M1 leak) | Process aborts with a heap out-of-memory error (seen in the M1 run: exit 134 after 230 ranges) | Fixed. A GC-based test fails if settled values stay reachable through a long-lived abort signal. The aborted run left data intact and the next run resumed | `apps/indexer/test/until-aborted.test.ts`; [m1-gate.md](m1-gate.md) |
| Alert delivery fails (Telegram unreachable, non-2xx) | Send error or non-2xx | Logged with the token redacted, never thrown; the same key is eligible again on the next occurrence. Without credentials alerts are log-only | `apps/indexer/test/alerts.test.ts` ("never throws on network failure, keeps the token out of logs, and retries on the next occurrence", "treats a non-2xx Telegram response as a failed delivery") |
| Indexer stalls without crashing (no head poll or commit) | `/healthz` returns 503 after `HEALTH_STALE_AFTER_MS`; head lag alert after `ALERT_HEAD_LAG_MS` above `ALERT_HEAD_LAG_BLOCKS` | Alert, nothing automatic. The health check does not touch the database, so a database outage cannot make the indexer look stalled by itself | `apps/indexer/test/status.int.test.ts`; `apps/indexer/test/alerts.test.ts` ("alerts only after lag stays above the threshold for the full duration") |
| Disk growth | Not measured by the indexer; watch the volume. Retention cycles log what they purged, `retention --dry-run` shows what is pending (with `manifestProblem`), and `/v1/status` `retention` shows how far purges reached | Retention (every `RETENTION_INTERVAL_MS`) deletes landing logs of published ranges after `LANDING_RETENTION_DAYS` and, when configured, decoded rows after `DECODED_RETENTION_DAYS`; blocks and `ops.*` are never deleted. Landing logs of a range stay unless it has a `match` reconciliation (when the reconciler is active); decoded rows stay unless landing is purged, the Parquet manifest covers the range and no unexported range shares its UTC day. A candidate, failed or concurrently backfilled range is never purged. If the volume fills anyway, Postgres fails writes, the run fails and resumes after space is freed. Size per setting: [costs-and-load.md](costs-and-load.md#storage) | `apps/indexer/test/retention.int.test.ts` ("deletes the logs of old published ranges and nothing else", "never purges a %s range" for candidate and failed, "needs a match row: a mismatch or no row at all blocks the range", "re-checks the status under the range lock...", "deletes decoded rows only after landing, only with a manifest that covers the range", "needs the manifest to cover the range, and a range sharing its UTC day with an unexported one waits", "is blocked while landing is not purged...", "lists what a cycle would purge, writes nothing, and matches what the cycle then does"); `apps/indexer/test/m3-e2e.int.test.ts` ("purges landing logs of published, reconciled ranges on its own timer; verify and rebuild-verify stay green"); `apps/indexer/test/lag.int.test.ts` (lag sample pruning). No test for disk-full |
| Database lost or corrupted | Connection errors; `verify` reports gaps or counts that do not add up | Postgres is the source of truth and there is no replica. Recovery is a restore from a backup, or re-ingestion from `START_BLOCK`, which is deterministic: the M1 run ingested 50,000 blocks in about an hour on keyless endpoints. Parquet files are derived and can be rebuilt from Postgres, not the other way round, except for days whose decoded rows were purged by retention: those exist only in Parquet, so back that store up too. Backups are an operator task and are not automated here | `verify` coverage: `apps/indexer/test/store.int.test.ts` (deleted log row, deleted range row, missing block height, duplicate positions). No restore drill has been run |

## Chain events

| Failure | Detection | Behaviour | Proof |
|---|---|---|---|
| Reorg inside the finalized window | A fetched range's first header does not extend the stored block below it (`ContinuityError`) | The resolver walks down from the tip in batches of 32 to the common ancestor, then in one transaction deletes every range reaching past it (whole ranges), writes an `ops.reorgs` row with orphaned and canonical blocks, and restarts ingest at the first deleted block. In-flight ranges are dropped. Published ranges at or below the ancestor are untouched | `apps/indexer/test/reorg.int.test.ts` (depths 1, 3 and 12; ancestor exactly at the finalized block; fork while the indexer was down; replay equals a fresh ingest; fork then fork back; fork during in-flight fetches); `apps/indexer/test/reorg.test.ts` (ancestor search); `apps/indexer/test/store.int.test.ts` (`rollbackTo`); `apps/indexer/test/anvil/reorg.anvil.test.ts` (real node, including two successive reorgs); `apps/indexer/test/m3-e2e.int.test.ts` (rollback while timers run). Live: one mainnet reorg, depth 1 |
| Continuity break that is not a fork (a node on another view) | Resolver finds the stored tip is still canonical (`no_fork`) | Nothing is deleted. The range is refetched with backoff; after 8 consecutive spurious breaks the run fails | `apps/indexer/test/reorg.test.ts` ("reports the tip itself as the ancestor when nothing diverges") covers the search only. The refetch and the limit of 8 have no dedicated test |
| Reorg at or below the finalized block | No common ancestor at or above `max(finalized, lowest stored block)` | An `ops.reorgs` row with action `halted`, nothing deleted, `fatal` log, halt alert, run `failed`, **exit code 2**. The halt is sticky: until `ack-halt <id> <text>` is run, every `run` start takes the lock, exits 2 before any RPC call, records a failed run and alerts (`halt-unacknowledged`), so a supervisor that restarts on any failure causes no provider traffic and no data change. After acknowledgement, a fork that is still there halts again as a new row. The finalized value is re-read at detection, not taken from the last poll | `apps/indexer/test/reorg.int.test.ts` ("halts with exit code 2 when the fork starts exactly at / far below the finalized block and deletes nothing", "judges the fork against finality as of detection", and in describe "a halt stays in force until it is acknowledged": "makes a restart exit 2 without a single RPC call, recording one failed run and alerting", "lets the run proceed after ack-halt and halts again, as a new unacknowledged row, when the fork is still there", "resumes ingesting after the acknowledgement once the provider serves the stored chain again", "ack-halt refuses bad usage, unknown ids and halts that are already acknowledged"); `apps/indexer/test/anvil/reorg.anvil.test.ts` ("halts with exit code 2 on a depth-N reorg" at the window size and window + 10) |
| Stored chain has a hole inside the ancestor window | The ancestor search compares block counts | Throws; nothing is deleted | `apps/indexer/test/reorg.test.ts` ("fails loudly if storage has a hole in the window") |

## Data quality

| Failure | Detection | Behaviour | Proof |
|---|---|---|---|
| A range fails one of the seven gates (`decode_rejects_zero`, `counts_consistent`, `blocks_linked`, `log_positions_unique`, `log_block_hash_matches`, `value_bounds`, `decoded_matches_landing`) | The quality cycle runs the gates on finalized candidate ranges; results are stored per range and gate in `ops.quality_results` | The range becomes `failed` and is not published. Exactly one backfill job is queued, a gate-failure alert fires (once per gate per cooldown). The API and the Parquet export never include it. A failed range is not re-gated; only its backfill changes it | `apps/indexer/test/quality.int.test.ts` (table of corruptions that must each fail the intended gate; "keeps one job and one result row per gate"; "does not re-gate a failed range"); `apps/api/test/api.int.test.ts` ("hides rows of a range the moment it leaves published"); `packages/analytics/test/analytics.int.test.ts` ("candidate and failed ranges never reach Parquet") |
| Range ends above the finalized block | `to_block > finalized` | Stays `candidate`, never gated or published. A range ending exactly at the finalized block is published | `apps/indexer/test/quality.int.test.ts` ("publishes a range ending exactly at the finalized block and not one ending a block above it") |
| Backfill cannot repair a range | Re-fetch fails, the re-fetched headers do not link to the stored neighbours, or a gate still fails | Job re-queued with the reason; data untouched; retried each cycle (2 jobs per cycle, least recently touched first). It will keep retrying indefinitely and needs a human ([runbook.md](runbook.md#stuck-backfill)) | `apps/indexer/test/quality.int.test.ts` ("refuses a re-fetch whose first header does not extend the stored block below...", "...last header is not the parent of the stored block above", "re-queues the job when the provider is unreachable...", "keeps the job queued, with the new reason, when the re-fetched data still fails a gate") |
| Backfill job left `running` by a crashed process | Next quality cycle finds a `running` job while holding the chain lock | Re-queued and worked normally. The same range can never have two jobs (id is `<chain>:<from>-<to>`) | `apps/indexer/test/quality.int.test.ts` ("picks up a job left running by a crashed process") |
| Reconciliation mismatch | Block hash or log identity or count differs from the second source | `ops.reconciliations` row with `mismatch`, alert, listed by `reconciliations --unexplained` until `explain-reconciliation` is run. Published data is not unpublished automatically; a human decides which side is right | `apps/indexer/test/reconcile.int.test.ts` (wrong hash at one height, differing last block hash, competing fork, observed null); `apps/indexer/test/m3-e2e.int.test.ts` ("records a mismatch when the second source misses a log, alerts, lists it as unexplained until explained") |
| Decoded tables drift from the landing logs (decoder bug, manual edit) | `rebuild-verify` | Exit 1 with up to five first differing positions per table. Reads only | `apps/indexer/test/rebuild.int.test.ts` (tampered value, deleted row, extra row, changed landing log, reject count disagreement); `apps/indexer/test/m3-e2e.int.test.ts` ("rebuild-verify exits 0 on clean data and 1 once a decoded row is tampered with") |
| Integrity damage in stored data (gaps, duplicates, missing blocks, orphan hash left stored) | `verify` | Exit 1 with a list of problems. An orphaned hash that was legitimately re-ingested after a fork back is accepted; halted rows' orphans are ignored | `apps/indexer/test/store.int.test.ts` (`verifyIntegrity` cases and "reorg audit" cases); `apps/indexer/test/reorg.int.test.ts` ("survives a fork and a fork back") |
| Parquet files tampered with, missing, stray or stale | `verifyAnalytics`: file hash, row count, sampled-day aggregates against SQL, full rebuild into a scratch directory | Failed check with the check name; a corrupt file is reported rather than thrown. The files are rebuildable from Postgres | `packages/analytics/test/analytics.int.test.ts` ("detects a tampered Parquet file by hash, rebuild and row-level aggregates", "still catches wrong numbers when the manifest was updated to match the tampered bytes", "reports a corrupt file as a failed check instead of throwing", "detects a missing and a stray partition") |
| Parquet day rewrite after decoded rows were purged (manifest deleted, or a late range published into a purged day) | The exporter checks, before writing, whether any day it would rewrite contains a decoded-purged range | Throws `refusing to export: day(s) ... contain ranges whose decoded rows were purged`, naming the day, and writes nothing, not even other pending days. The Parquet files for purged days are then the only copy of those rows, so they must be backed up and never deleted. Later days still export incrementally. `analytics verify` compares Postgres with Parquet only for days fully retained in Postgres and lists the rest as `purgedDays`; file checks still cover every day | `packages/analytics/test/analytics.int.test.ts` ("refuses to rewrite a purged day when the manifest is gone, naming the day and leaving every file untouched", "refuses a pending range that lands in a purged day, and writes nothing, not even the other pending days", "still exports later days incrementally while earlier days are purged and already in the manifest", and under "after retention purged decoded rows": "compares only the days still fully in Postgres and reports the purged day", "skips everything Postgres-based once every day is purged, leaving the file checks"). Losing the Parquet store after purges has no recovery path in this repository |

## API

| Failure | Detection | Behaviour | Proof |
|---|---|---|---|
| Database unreachable from the API | `select 1` fails in `/healthz` or a query fails | `/healthz` returns 503; other routes return a generic 500 envelope without internals | `apps/api/test/api.int.test.ts` ("reports ok while the database answers and 503 once it does not", "does not leak internals when a handler fails") |
| Forged, malformed or foreign cursor, bad parameters | Cursor shape re-validated on decode; Zod validation before any I/O | 400 with `invalid_cursor` or `bad_request`; the database is never reached | `apps/api/test/http.test.ts`; `apps/api/test/validation.test.ts`; `apps/api/test/api.int.test.ts` ("rejects malformed and foreign cursors with 400 invalid_cursor") |
| Rows appear or move while a client pages | Keyset cursor on `(block_number, log_index)` | Every row is seen exactly once in order, including when newer ranges are committed and published mid-walk | `apps/api/test/api.int.test.ts` ("walks every row exactly once in newest-first order for any page size", "is stable while newer ranges are committed and published mid-walk") |
| Indexer is down | The dashboard status page is computed from the database alone | The API keeps serving published data; the status page shows lag growing | `apps/api/test/api.int.test.ts` ("derives positions, lag and evidence from the database alone"); `apps/web/e2e/overview.spec.ts` (head and finalized lag shown from seeded data) |

## Not covered

- No authentication, so a public API address is a public read of everything the API serves ([decisions.md](decisions.md#adr-016-read-only-api-with-fail-closed-queries-and-keyset-pagination)).
- No standby indexer and no database replica: recovery from a lost host is restore or re-ingest.
- A provider pair that shares an upstream node and gives the same wrong answer defeats both ingestion and reconciliation.
- Etherscan, the third completeness source, checks a random sample of finalized ranges, not all of them (tests: `apps/indexer/test/etherscan.test.ts`, `etherscan.int.test.ts`).
- Disk exhaustion is handled by operator monitoring, not by the code.
- Seen live once: on 2026-10-28 an ingest provider answered a fresh block (26,288,697) with no logs. The block was stored with 0 logs and published after all seven gates passed, because the gates only check what is stored. The second-source reconciler caught it three minutes after publication (stored 0, observed 56). All five configured providers returned 64 logs for the block on 2026-11-01, and it was repaired through the manual backfill entry point in the [runbook](runbook.md#reconciliation-mismatch). A gate that compares each block header's logs bloom with its stored logs would catch this class before publication; it is not built.
